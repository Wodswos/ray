# Ray Core - GCS InternalKV 调用栈分析

## InternalKV Put 调用链

以 `internal_kv_put` 为例，追踪从 Python 到 Redis 的完整调用栈：

```
Python/Cython: InnerGcsClient.internal_kv_put()
  → self.inner.get().InternalKV().Put()
    → C++ GcsClient.InternalKV()
      → InternalKVAccessor.Put() (sync wrapper)
        → InternalKVAccessor.AsyncInternalKVPut()
          → GcsRpcClient.InternalKVPut() (gRPC call)
            → GCS Server: GcsInternalKVManager.HandleInternalKVPut()
              → StoreClientInternalKV.Put()
                → RedisStoreClient.AsyncPut()
                  → Redis HSET/HSETNX command
```

### 1. Cython 层

**文件**: `python/ray/includes/gcs_client.pxi` (行 129-130)

```python
status = self.inner.get().InternalKV().Put(
    ns, key, value, overwrite, timeout_ms, opt_added.value())
```

- `self.inner` 是 `shared_ptr[CGcsClient]`（行 43），`.get()` 取出裸指针
- `.InternalKV()` 返回 `InternalKVAccessor` 引用
- `.Put()` 是同步 C++ 调用，在 `with nogil` 块中执行（释放 Python GIL）
- 返回值：`overwrite=false` 时 `HSETNX` 返回是否新增（1/0），`overwrite=true` 时 `HSET` 总是覆盖

### 2. C++ GcsClient 层

**文件**: `src/ray/gcs_rpc_client/gcs_client.h` (行 232)

```cpp
InternalKVAccessor &InternalKV() { return internal_kv_accessor_; }
```

- `GcsClient` 持有各类型的 accessor，`InternalKV()` 返回 `InternalKVAccessor` 引用
- accessor 在 `GcsClient::Connect()` 时初始化，绑定到对应的 `GcsRpcClient`

### 3. InternalKVAccessor 层

**文件**: `src/ray/gcs_rpc_client/accessor.cc` (行 852-869)

```cpp
Status InternalKVAccessor::AsyncInternalKVPut(
    const std::string &namespace_,
    const std::string &key,
    const std::string &value,
    bool overwrite,
    int64_t timeout_ms,
    OptionalItemCallback<bool> callback) {
  rpc::InternalKVPutRequest request;
  request.set_key(key);
  request.set_value(value);
  request.set_overwrite(overwrite);
```

- 构造 `rpc::InternalKVPutRequest` protobuf 消息，填入 key/value/overwrite/namespace
- 同步 `Put()` 方法内部通过 `SyncCall()` 包装异步调用，等待 gRPC 返回后填充 `opt_added`

### 4. GcsRpcClient 层

**文件**: `src/ray/gcs_rpc_client/rpc_client.h` (行 498-501)


- 通过宏生成 `InternalKVPut()` 方法，向 GCS 服务端发起 gRPC 调用

### 6. GCS 服务端处理

**文件**: `src/ray/gcs/gcs_kv_manager.cc` (行 74-93)

```cpp
void GcsInternalKVManager::HandleInternalKVPut(
    rpc::InternalKVPutRequest request,
    rpc::InternalKVPutReply *reply,
    rpc::SendReplyCallback send_reply_callback) {
  // 校验 key 格式
  auto status = ValidateKey(request.key());
  if (!status.ok()) { ... }
  // 调用底层存储
  store_client_->Put(request.namespace_(), request.key(),
                     request.value(), request.overwrite(), ...);
}
```

- 校验 key 不含非法前缀（如 `RAY{cluster}@`）
- 调用 `StoreClientInternalKV::Put()`

### 7. StoreClientInternalKV 层

**文件**: `src/ray/gcs/store_client_kv.cc` (行 93-100)

```cpp
Status StoreClientInternalKV::Put(...) {
  auto full_key = MakeKey(ns, key);  // 组合 namespace + key
  return store_client_->AsyncPut(table_name, full_key, value, overwrite, ...);
}
```

- `MakeKey(ns, key)` 将 namespace 和 key 组合为 `{namespace}:{original_key}`
- `table_name` 为 `RAY{cluster}@KV`（Redis hash table 名）
- 委托给底层 `StoreClient::AsyncPut`

### 8. Redis 存储层

**文件**: `src/ray/gcs/store_client/redis_store_client.cc`

- `overwrite=true`: 执行 Redis `HSET` 命令，总是覆盖已有值
- `overwrite=false`: 执行 Redis `HSETNX` 命令，仅在 key 不存在时设置，返回是否新增
- Redis hash key: `RAY{cluster}@KV`，field: `{namespace}:{original_key}`

## 其他 InternalKV 方法

Del / Get / Keys / MultiGet 调用链结构类似，区别仅在：
- accessor 层构造对应的 Request protobuf
- proto 中对应不同的 RPC 方法
- 服务端调用 StoreClient 的不同方法（AsyncDel / AsyncGet 等）
- Redis 层使用不同命令（DEL / HGET / HKEYS 等）

## InternalKV 存储实现架构

### 整体分层

```
Python 客户端 (internal_kv.py)
       │ gRPC
       ↓
GcsInternalKVManager (gcs_kv_manager.cc)   ← RPC handler，校验 key 后转发请求
       │
       ↓
StoreClientInternalKV (store_client_kv.cc)  ← 适配层，给 key 加 namespace 前缀
       │
       ↓
StoreClient (抽象接口)
       │
   ┌───┴───┐
   ↓       ↓
InMemory   RedisStoreClient   ← 实际存储后端（由配置决定）
```

### 1. GcsInternalKVManager — RPC Handler 层

**文件**: `src/ray/gcs/gcs_kv_manager.cc` (行 28-157)

`GcsInternalKVManager` 实现 `rpc::InternalKVGcsServiceHandler` 接口，每个 RPC 方法（Get/Put/Del/Exists/Keys/MultiGet）的处理逻辑统一为：

1. `ValidateKey(request.key())` — 校验 key 不能以 `@namespace_` 开头（这是内部保留前缀）
2. 委托给 `kv_instance_`（一个 `InternalKVInterface` 实现）执行实际操作
3. 回调中填充 reply 并通过 `GCS_RPC_SEND_REPLY` 返回 gRPC 响应

特殊 RPC：`HandleGetInternalConfig` 不走 KV 存储，直接返回 `raylet_config_list_`（Ray 集群配置 JSON）。

### 2. StoreClientInternalKV — Namespace 适配层

**文件**: `src/ray/gcs/store_client_kv.cc` (行 27-149)

`StoreClientInternalKV` 桥接 `InternalKVInterface` 和底层 `StoreClient`，核心职责是 **namespace 编码/解码**：

```cpp
// Key 编码：将 (namespace, key) 合成 Redis 中的完整 field 名
std::string MakeKey(const std::string &ns, const std::string &key) {
  if (ns.empty()) return key;
  return "@namespace_" + ns + ":" + key;
  // 例: @namespace_FunctionTable:RemoteFunction:...
}

// Key 解码：从 Redis field 名还原原始 key（去掉 namespace 前缀）
std::string ExtractKey(const std::string &key) {
  if (absl::StartsWith(key, "@namespace_")) {
    // 按第一个 ":" 分割，返回后半部分
    return parts[1];
  }
  return key;
}
```

所有操作先将 `(ns, key)` 合成 `MakeKey(ns, key)` 再传给 `StoreClient`，读取时 `ExtractKey` 剻掉前缀还原原始 key。

`table_name_` 固定为 `"KV"`（来自 protobuf `TablePrefix::KV` 的枚举名）。

`Put` 方法语义特殊：
- `overwrite=true` → `AsyncPut(..., overwrite=true)`，覆盖已有值，回调返回 `false`（非新增）
- `overwrite=false` → `AsyncPut(..., overwrite=false)`，仅新增不覆盖，回调返回 `true`（新增成功）/ `false`（已存在）

### 3. StoreClient 抽象接口

**文件**: `src/ray/gcs/store_client/store_client.h` (行 33-122)

`StoreClient` 是纯虚类，定义了异步 KV 操作接口：

| 方法 | 说明 |
|------|------|
| `AsyncPut(table, key, data, overwrite, callback)` | 写入，overwrite 控制覆盖/仅新增 |
| `AsyncGet(table, key, callback)` | 读取单个 key |
| `AsyncMultiGet(table, keys, callback)` | 批量读取 |
| `AsyncGetAll(table, callback)` | 读取整个表 |
| `AsyncDelete(table, key, callback)` | 删除单个 key |
| `AsyncBatchDelete(table, keys, callback)` | 批量删除 |
| `AsyncGetKeys(table, prefix, callback)` | 按前缀扫描所有 key |
| `AsyncExists(table, key, callback)` | 检查 key 是否存在 |
| `AsyncGetNextJobID(callback)` | 自增获取下一个 Job ID |

所有方法都是异步的，通过 `Postable<void(...)>` 回调返回结果。

### 4. 存储后端选择

**文件**: `src/ray/gcs/gcs_server.cc` (行 594-609)

GCS Server 通过 `GetStorageType()` 决定使用哪种后端：

```cpp
GcsServer::StorageType GcsServer::GetStorageType() const {
  if (RayConfig::instance().gcs_storage() == kInMemoryStorage) {
    if (!config_.redis_address.empty()) {
      return StorageType::REDIS_PERSIST;  // 配置 memory 但有 Redis → 用 Redis
    }
    return StorageType::IN_MEMORY;
  }
  if (RayConfig::instance().gcs_storage() == kRedisStorage) {
    RAY_CHECK(!config_.redis_address.empty());
    return StorageType::REDIS_PERSIST;
  }
}
```

| 配置                     | Redis 地址 | 实际后端                                  |
| ---------------------- | -------- | ------------------------------------- |
| `gcs_storage="memory"` | 无        | `InMemoryStoreClient` — 进程内存，重启丢失     |
| `gcs_storage="memory"` | 有        | `RedisStoreClient` — 有 Redis 就用 Redis |
| `gcs_storage="redis"`  | 必须有      | `RedisStoreClient` — Redis 持久存储       |

两者都被 `ObservableStoreClient` 包装，加 latency/count metrics。

### 5. RedisStoreClient — Redis HASH 存储

**文件**: `src/ray/gcs/store_client/redis_store_client.h`, `redis_store_client.cc`

使用 Redis **HASH** 作为存储结构：

```
HASH key:  "RAY" + external_storage_namespace + "@" + table_name
           例: "RAY@KV"
field:     MakeKey(ns, key) 编码后的完整 key
           例: "@namespace_FunctionTable:RemoteFunction:01000000:a3f2..."
value:     用户写入的 bytes
           例: pickle.dumps({metadata_dict})
```

| 操作 | Redis 命令 | 说明 |
|------|-----------|------|
| Put overwrite=true | `HSET` | 总是覆盖，返回值忽略 |
| Put overwrite=false | `HSETNX` | 仅新增，返回 1=新增 / 0=已存在 |
| Get | `HGET` | 读取单个 field |
| MultiGet | `HMGET` | 批量读取多个 field |
| Delete | `HDEL` | 删除单个 field |
| BatchDelete | `HDEL` (多 key) | 批量删除 |
| GetKeys | `HKEYS` + 前缀过滤 | 扫描所有 field，Python 端再做前缀匹配 |
| Exists | `HEXISTS` | 检查 field 是否存在 |

注意：`GetKeys` 在 Redis 端先 `HKEYS` 取出全部 field，再在 C++ 端做前缀过滤。这在 field 数量多时可能有性能问题。

### 6. InMemoryStoreClient — 内存存储

**文件**: `src/ray/gcs/store_client/in_memory_store_client.h`, `in_memory_store_client.cc`

线程安全的内存实现，使用 `ConcurrentFlatMap` 存储数据：

```
结构: map<table_name, ConcurrentFlatMap<key, value>>
例: {"KV": {"@namespace_FunctionTable:RemoteFunction:...": pickle_bytes, ...}}
```

所有操作都是原子性的，数据仅在进程生命周期内存在，重启丢失。主要用于测试和开发环境。

### 7. 函数序列化数据在 Redis 中的实际存储

以远程函数导出为例，最终在 Redis 中的存储结构：

```
Redis HASH key:  "RAY@KV"
Redis field:     "@namespace_FunctionTable:RemoteFunction:<job_id_hex>:<function_id_hex>"
Redis value:     pickle.dumps({
                    "job_id": bytes,
                    "function_id": bytes,
                    "function_name": str,
                    "module": str,
                    "function": cloudpickle.dumps(original_function),  # 内层序列化
                    "collision_identifier": sha1_hash,
                    "max_calls": int,
                 })
```

两层序列化：
- **内层** `cloudpickle.dumps(function)`：序列化函数字节码+闭包
- **外层** `pickle.dumps(dict)`：序列化包含内层 bytes 的元信息字典
