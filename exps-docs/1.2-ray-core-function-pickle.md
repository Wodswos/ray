# Ray Function Serialization & Deserialization 逻辑详解

## 概述

Ray 将用户定义的 Python 函数（`@ray.remote` 装饰的远程函数 / Actor 类）从 Driver 进程序列化后存入 GCS，Worker 进程在执行 Task 时从 GCS 取出并反序列化，最终调用原始函数。整个流程围绕 **cloudpickle**（Ray 内嵌的 fork 版本 v3.0.0）完成 Python 函数及其闭包的序列化。

---

## 1. 序列化入口 — Driver 端

### 1.1 RemoteFunction 初始化

[remote_function.py:91-171](python/ray/remote_function.py#L91-L171)

`@ray.remote` 装饰函数时创建 `RemoteFunction` 对象。此时**不做 pickle**，仅记录原始函数引用和元信息：

```python
self._function = function           # 原始 Python 函数对象
self._function_name = function.__module__ + "." + function.__name__
self._function_descriptor = function_descriptor  # 初始 descriptor（可能未最终确定）
self._uuid = uuid.uuid4()          # 用于生成唯一 function_id
```

关键：`_pickled_function` 此时**不存在**，序列化延迟到首次 `.remote()` 调用时执行。

### 1.2 首次 `.remote()` 触发序列化

[remote_function.py:348-373](python/ray/remote_function.py#L348-L373)

当用户调用 `func.remote()` 提交 Task 时，`_remote()` 方法检查是否需要导出函数：

```python
if (
    not self._is_cross_language
    and self._last_export_cluster_and_job != worker.current_cluster_and_job
):
    # 1. 生成最终 function_descriptor
    self._function_descriptor = PythonFunctionDescriptor.from_function(
        self._function, self._uuid
    )
    # 2. 序列化函数
    self._pickled_function = pickle_dumps(
        self._function,
        f"Could not serialize the function {self._function_descriptor.repr}",
    )
    # 3. 记录已导出标记，避免重复导出
    self._last_export_cluster_and_job = worker.current_cluster_and_job
    # 4. 导出到 GCS
    worker.function_actor_manager.export(self)
```

**为什么延迟到首次调用？**
- `@ray.remote` 定义时 `ray.init()` 可能尚未调用，序列化需要运行时上下文
- 同一脚本的第二个 Driver 应独立序列化（闭包变量可能已变化），所以用 `_last_export_cluster_and_job` 判断是否需要重新 pickle

## 2. 序列化核心 — pickle_dumps & cloudpickle

### 2.1 pickle_dumps 包装

[serialization.py:21-34](python/ray/_common/serialization.py#L21-L34)

`pickle_dumps` 是 `cloudpickle.dumps` 的增强包装，提供更好的错误信息：

```python
def pickle_dumps(obj: Any, error_msg: str):
    try:
        return pickle.dumps(obj)       # pickle = ray.cloudpickle
    except (TypeError, OufOfBandObjectRefSerializationException) as e:
        sio = io.StringIO()
        inspect_serializability(obj, print_file=sio)  # 分析不可序列化原因
        msg = f"{error_msg}:\n{sio.getvalue()}"
        if isinstance(e, TypeError):
            raise TypeError(msg) from e
        else:
            raise OufOfBandObjectRefSerializationException(msg)
```

失败时会调用 `inspect_serializability` 深度分析对象的哪些属性/闭包变量不可序列化，输出详细诊断。

### 2.2 Ray 的 cloudpickle fork

[cloudpickle/__init__.py](python/ray/cloudpickle/__init__.py)

Ray 内嵌 cloudpickle v3.0.0，直接 `from ray.cloudpickle.cloudpickle_fast import CloudPickler, dumps, dump`。相比标准 pickle，cloudpickle 能序列化：

- **闭包函数**：捕获的局部变量一并序列化
- **lambda / 动态定义的函数**：在交互式 REPL 或 `__main__` 中定义的函数
- **嵌套函数**：函数内部定义的子函数
- **交互式环境中的对象**：`__main__` 模块定义的类和函数

cloudpickle 的原理是将函数的**字节码**（`code` 对象）连同其闭包变量逐个序列化，而非依赖模块名查找（标准 pickle 的方式）。这使得函数可以在完全不同的进程中被还原，无需源文件在目标进程的 `sys.path` 中。

### 2.3 cloudpickle 序列化实现细节

#### 2.3.1 入口：save_function 的分叉逻辑

[cloudpickle/cloudpickle.py:1402-1415](python/ray/cloudpickle/cloudpickle.py#L1402-L1415)

`CloudPickler.save_function` 是函数序列化的入口，根据函数是否可按引用序列化分叉：

```python
def save_function(self, obj, name=None):
    if _should_pickle_by_reference(obj, name=name):
        return super().save_global(obj, name=name)    # ← 传引用：只记录模块名+函数名
    elif PYPY and isinstance(obj.__code__, builtin_code_type):
        return self.save_pypy_builtin_func(obj)
    else:
        return self._save_reduce_pickle5(
            *self._dynamic_function_reduce(obj), obj=obj
        )                                              # ← 传值：完整序列化函数
```

**`_should_pickle_by_reference` 的判定逻辑**：

[cloudpickle/cloudpickle.py:228-261](python/ray/cloudpickle/cloudpickle.py#L228-L261)

1. 通过 `_lookup_module_and_qualname` 查找函数是否属于某个可 import 的模块的顶层属性
2. 如果找到，检查该模块是否被 `register_pickle_by_value` 注册为按值序列化（默认未注册）
3. 最终结果：只有"属于可 import 模块的顶层属性"的函数才走传引用路径

**典型场景**：
- `def f(): ...` 在 `__main__` 或 REPL 中定义 → `_should_pickle_by_reference` 返回 False → 传值序列化
- `def f(): ...` 在已安装的 `my_module.py` 中定义 → 传引用（只存模块名）
- `lambda x: x + 1` → 无法按引用序列化 → 传值序列化

> 本文聚焦于**传值序列化**分支（即 `_dynamic_function_reduce` 路径），因为这是 Ray 远程函数的核心场景。

#### 2.3.2 传值序列化的完整调用链

[cloudpickle/cloudpickle.py:1189-1194](python/ray/cloudpickle/cloudpickle.py#L1189-L1194)

`_dynamic_function_reduce` 将函数拆解为六个组成部分，对应 pickle 的 `__reduce__` 协议：

```python
def _dynamic_function_reduce(self, func):
    newargs = self._function_getnewargs(func)   # 构造函数的参数
    state = _function_getstate(func)            # 函数的状态（__dict__ + slotstate）
    return (_make_function, newargs, state, None, None, _function_setstate)
    #        reconstructor  newargs  state   list   dict   setstate
```

反序列化时，Python 的 pickle 机制会：
1. 调用 `_make_function(*newargs)` 创建函数骨架
2. 调用 `_function_setstate(func, state)` 将状态还原到函数上

#### 2.3.3 _function_getnewargs — 函数骨架的构造参数

[cloudpickle/cloudpickle.py:1210-1241](python/ray/cloudpickle/cloudpickle.py#L1210-L1241)

`_function_getnewargs` 返回 `types.FunctionType(code, globals, name, argdefs, closure)` 的参数：

```python
def _function_getnewargs(self, func):
    code = func.__code__

    # 1. base_globals：新建空 dict，只填入模块元信息
    base_globals = self.globals_ref.setdefault(id(func.__globals__), {})
    if base_globals == {}:
        for k in ["__package__", "__name__", "__path__", "__file__"]:
            if k in func.__globals__:
                base_globals[k] = func.__globals__[k]

    # 2. closure：用空 cell 替代真实值（避免递归序列化）
    if func.__closure__ is None:
        closure = None
    else:
        closure = tuple(_make_empty_cell() for _ in range(len(code.co_freevars)))

    return code, base_globals, None, None, closure
```

**关键设计**：
- `base_globals` 是一个**空字典**（只含模块名等元信息），真实全局引用在 `_function_getstate` 中单独处理。这样解耦是因为 `types.FunctionType` 构造函数要求 globals 是一个 dict，但真实内容延迟填充
- `closure` 使用**空 cell**（而非真实值），真实 cell 值在 `_function_getstate` 中处理。这避免了在构造阶段序列化闭包值导致的递归问题（闭包值本身可能引用同一函数）

#### 2.3.4 _function_getstate — 函数的完整状态（主要体积来源）

[cloudpickle/cloudpickle.py:689-725](python/ray/cloudpickle/cloudpickle.py#L689-L725)

`_function_getstate` 返回 `(state, slotstate)`，其中 `state = func.__dict__`（动态属性），`slotstate` 包含函数的所有核心属性：

```python
slotstate = {
    "__name__":        func.__name__,
    "__qualname__":    func.__qualname__,
    "__annotations__": func.__annotations__,
    "__kwdefaults__":  func.__kwdefaults__,
    "__defaults__":    func.__defaults__,
    "__module__":      func.__module__,
    "__doc__":         func.__doc__,
    "__closure__":     func.__closure__,
}

# ↓↓ 以下两项是体积的主要贡献者 ↓↓

# 1. 全局引用：扫描字节码找出所有 LOAD_GLOBAL / STORE_GLOBAL / DELETE_GLOBAL
f_globals_ref = _extract_code_globals(func.__code__)
f_globals = {k: func.__globals__[k] for k in f_globals_ref if k in func.__globals__}

# 2. 闭包值：提取每个 cell 的真实内容
if func.__closure__ is not None:
    closure_values = list(map(_get_cell_contents, func.__closure__))
else:
    closure_values = ()

# 3. 子模块依赖：查找函数间接引用的子模块
slotstate["_cloudpickle_submodules"] = _find_imported_submodules(
    func.__code__, itertools.chain(f_globals.values(), closure_values)
)

slotstate["__globals__"] = f_globals
```

#### 2.3.4a code 对象是什么

Python 的 `code` 对象（`types.CodeType`）是函数编译后的**底层表示**，是 CPython 解释器执行的"机器码"。当 Python 编译器处理 `def f(x): return x + 1` 时：

1. 将源代码编译为字节码指令流（类似汇编语言的指令序列）
2. 将字节码和所有元信息打包成一个不可变的 `code` 对象

code 对象包含函数执行所需的**一切静态信息**：

| 属性 | 含义 | 示例 |
|------|------|------|
| `co_code` | 字节码指令流（bytes） | `b'\x7c\x00\x01\x00S\x00'` |
| `co_consts` | 常量池（数字、字符串、嵌套函数的 code 对象） | `(None, 1)` |
| `co_names` | 全局/属性名称列表 | `('add', 'numpy')` |
| `co_varnames` | 局部变量名列表 | `('x',)` |
| `co_argcount` | 参数数量 | `1` |
| `co_freevars` | 闭包引用的外部变量名 | `('y',)` |
| `co_cellvars` | 被内部嵌套函数引用的变量名 | `('z',)` |

code 对象是**不可变的**、与函数定义绑定的静态数据。它只描述"怎么做"（指令流），不包含"依赖什么"（全局变量、闭包值）。

函数对象与 code 对象的关系：

```
FunctionType = code 对象 + __globals__ + __closure__ + __defaults__ + __name__ + ...
```

code 对象是函数的"骨架"，`__globals__` 和 `__closure__` 是骨架的"血肉"——它们提供运行时所需的动态数据。

#### 2.3.4b 函数依赖的模块如何被序列化

当函数引用了外部模块（如 `import numpy as np; np.array(...)`），cloudpickle 通过 `_module_reduce` 处理模块对象的序列化，有两条路径：

**路径 A：按引用序列化（`subimport`）— 绝大多数情况**

[cloudpickle/cloudpickle.py:968-970](python/ray/cloudpickle/cloudpickle.py#L968-L970)

```python
def _module_reduce(obj):
    if _should_pickle_by_reference(obj):
        return subimport, (obj.__name__,)   # ← 只序列化一个模块名字符串！
```

反序列化时调用 `subimport(name)`：

[cloudpickle/cloudpickle.py:452-458](python/ray/cloudpickle/cloudpickle.py#L452-L458)

```python
def subimport(name):
    __import__(name)          # 在目标进程中 import 这个模块
    return sys.modules[name]  # 返回已加载的模块对象
```

**对于可 import 的模块（如 numpy、os、concurrent.futures），序列化结果只是一个模块名字符串**，反序列化时通过 `import` 重建。整个 numpy 库不会被打包进 `_pickled_function`。

**路径 B：按值序列化（`dynamic_subimport`）— 动态创建的模块**

[cloudpickle/cloudpickle.py:971-978](python/ray/cloudpickle/cloudpickle.py#L971-L978)

```python
else:
    state = obj.__dict__.copy()
    state.pop("__builtins__", None)
    return dynamic_subimport, (obj.__name__, state)   # 序列化模块名 + __dict__ 全部内容
```

反序列化时：

[cloudpickle/cloudpickle.py:461-465](python/ray/cloudpickle/cloudpickle.py#L461-L465)

```python
def dynamic_subimport(name, vars):
    mod = types.ModuleType(name)          # 创建新的空模块
    mod.__dict__.update(vars)             # 把原模块的所有属性灌进去
    mod.__dict__["__builtins__"] = builtins.__dict__
    return mod
```

这条路径只在模块**不在 `sys.modules` 中**时触发（模块是动态创建的，如 `types.ModuleType("my_dyn_mod")`），属于罕见场景。此时模块的 `__dict__` 全部内容会被序列化。

**完整示例：函数引用 `np.array` 时的序列化流程**

```
函数源码:  import numpy as np
           @ray.remote
           def f(x): return np.array(x)

序列化时:
  1. _extract_code_globals 扫描字节码 → 发现全局引用名 "np"
  2. 从 func.__globals__["np"] 取出 numpy 模块对象
  3. numpy 模块走 _module_reduce → _should_pickle_by_reference 返回 True
     → 只序列化字符串 "numpy"（约 6 bytes）

反序列化时（Worker 进程）:
  1. subimport("numpy") → Worker 进程执行 import numpy → 得到 numpy 模块对象
  2. _function_setstate 将 numpy 模块填入 func.__globals__["np"]
  3. 函数中 LOAD_GLOBAL "np" + LOAD_ATTR "array" 正常执行
```

**关键结论**：
- 模块依赖的序列化开销**几乎为零**（仅一个字符串）
- 前提是 Worker 端能 `import` 到该模块。如果 Worker 缺少依赖库，`import numpy` 会失败，函数反序列化也会失败——这是 Ray 要求 Driver 和 Worker Python 环境一致的原因之一
- 模块中的具体对象（如 `np.array`）不会被单独序列化。反序列化后通过 `getattr(module, name)` 自然还原

#### 2.3.5 _extract_code_globals — 如何确定哪些全局变量需要序列化

[cloudpickle/cloudpickle.py:304-326](python/ray/cloudpickle/cloudpickle.py#L304-L326)

```python
def _extract_code_globals(co):
    """Find all globals names read or written to by codeblock co."""
    out_names = _extract_code_globals_cache.get(co)
    if out_names is None:
        # 用 dict（而非 set）保证确定性顺序，避免 pickle bytes 不稳定
        out_names = {name: None for name in _walk_global_ops(co)}

        # 递归扫描嵌套函数的 code 对象（在 co_consts 中）
        if co.co_consts:
            for const in co.co_consts:
                if isinstance(const, types.CodeType):
                    out_names.update(_extract_code_globals(const))

        _extract_code_globals_cache[co] = out_names
    return out_names
```

底层通过 `_walk_global_ops` 扫描字节码指令：

```python
def _walk_global_ops(code):
    """Yield referenced name for global-referencing instructions in code."""
    for instr in dis.get_instructions(code):
        op = instr.opcode
        if op in GLOBAL_OPS:          # LOAD_GLOBAL, STORE_GLOBAL, DELETE_GLOBAL
            yield instr.argval
```

**重要细节**：`_extract_code_globals` 会**递归扫描嵌套函数**。如果函数内部定义了子函数，子函数引用的全局变量也会被包含。这可能导致序列化的全局变量数量远超函数直接引用的数量。

#### 2.3.6 _code_reduce — code 对象的序列化

[cloudpickle/cloudpickle.py:799-894](python/ray/cloudpickle/cloudpickle.py#L799-L894)

code 对象通过 `_code_reduce` 拆解为 `types.CodeType` 构造参数的元组。Python 3.11+ 版本包含最多 17 个字段：

```python
def _code_reduce(obj):
    args = (
        obj.co_argcount,         # 参数数量
        obj.co_posonlyargcount,  # 仅位置参数数量
        obj.co_kwonlyargcount,   # 仅关键字参数数量
        obj.co_nlocals,          # 局部变量数量
        obj.co_stacksize,        #栈大小
        obj.co_flags,            # 标志位
        obj.co_code,             # ← 字节码指令（bytes，通常很小）
        obj.co_consts,           # ← 常量列表（可能含嵌套函数的 code 对象！）
        obj.co_names,            # 全局名称列表
        obj.co_varnames,         # 局部变量名列表
        obj.co_filename,         # 源文件名
        obj.co_name,             # 函数名
        obj.co_qualname,         # 完整函数名（Python 3.11+）
        obj.co_firstlineno,      # 首行号
        obj.co_linetable,        # 行号表（Python 3.10+）
        obj.co_exceptiontable,   # 异常表（Python 3.11+）
        obj.co_freevars,         # 自由变量名列表
        obj.co_cellvars,         # cell 变量名列表
    )
    return types.CodeType, args
```

**注意**：`co_consts` 中可能包含嵌套函数的 code 对象，这些 code 对象也会递归走 `_code_reduce` 序列化。因此嵌套函数越多，code 对象部分的体积越大。

#### 2.3.7 _find_imported_submodules — 子模块依赖的发现

[cloudpickle/cloudpickle.py:329-375](python/ray/cloudpickle/cloudpickle.py#L329-L375)

```python
def _find_imported_submodules(code, top_level_dependencies):
    """Find currently imported submodules used by a function."""
    subimports = []
    for x in top_level_dependencies:           # 遍历 globals + closure_values
        if isinstance(x, types.ModuleType) and hasattr(x, "__package__") and x.__package__:
            prefix = x.__name__ + "."           # 如 "concurrent."
            for name in list(sys.modules):
                if name is not None and name.startswith(prefix):
                    # 检查函数的字节码是否引用了这个子模块的属性
                    tokens = set(name[len(prefix):].split("."))  # 如 {"futures"}
                    if not tokens - set(code.co_names):           # co_names 包含所有名字引用
                        subimports.append(sys.modules[name])
    return subimports
```

这个函数解决的问题是：函数引用 `concurrent.futures.ThreadPoolExecutor` 时，`_extract_code_globals` 只会抓到 `concurrent`（全局引用名），但实际需要的是 `concurrent.futures` 子模块。`_find_imported_submodules` 通过检查 `sys.modules` 和 `co_names` 补齐这类间接子模块依赖。

子模块本身只存名称引用（不序列化模块内容），对体积影响很小。

### 2.4 _pickled_function 体积评估

#### 2.4.1 体积组成分解

`_pickled_function = cloudpickle.dumps(func)` 的字节流由以下部分构成，按**对体积的贡献**从大到小排列：

| 组成部分 | 来源 | 体积特征 | 典型占比 |
|----------|------|----------|---------|
| **`__globals__` 引用对象** | `_function_getstate` → `f_globals` | **最大变量**。每个引用的对象被递归完整序列化。若引用大型对象（模型权重、大 dict/list），体积可膨胀至 MiB 级 | 50-90%+ |
| **`__closure__` cell 值** | `_function_getstate` → `closure_values` | 闭包捕获的每个自由变量的值被完整序列化。若捕获大对象，与 globals 同理 | 0-40% |
| **`__defaults__` / `__kwdefaults__`** | `_function_getstate` → slotstate | 默认参数值被序列化。若默认值是大对象（如预加载的数据），贡献显著 | 0-30% |
| **`__code__` 对象** | `_function_getnewargs` → code → `_code_reduce` | 字节码本身很小，但 `co_consts` 可能含嵌套函数的 code 对象（递归膨胀）。`co_names`/`co_varnames` 等字符串元信息有固定开销 | 1-10% |
| **`__annotations__`** | `_function_getstate` → slotstate | 类型注解中的类型对象会被序列化。复杂类型（如 Pydantic model、Generic 类型）可显著增加体积 | 0-5% |
| **`_cloudpickle_submodules`** | `_function_getstate` → slotstate | 仅存储模块名称列表（字符串），体积很小 | <1% |
| **其他元信息** | `__name__`, `__qualname__`, `__module__`, `__doc__` | 纯字符串，体积极小 | <1% |

**核心结论**：`_pickled_function` 的体积主要由**函数引用的外部对象**决定，而非函数本身的代码。一个只有 5 行代码的函数，如果闭包捕获了一个 100 MiB 的 numpy 数组，其 `_pickled_function` 就会是 ~100 MiB。

#### 2.4.2 如何细致评估体积

**方法一：直接测量 total**

```python
import ray
import ray.cloudpickle as pickle

pickled = pickle.dumps(my_func)
total_size = len(pickled)
print(f"Total pickled size: {total_size} bytes ({total_size / 1024 / 1024:.2f} MiB)")
```

**方法二：逐层拆解各组成部分**

利用 cloudpickle 的内部方法，可以逐项测量每个组成部分的大小：

```python
import ray.cloudpickle as pickle
from ray.cloudpickle.cloudpickle import (
    _extract_code_globals, _function_getstate, _find_imported_submodules,
    _code_reduce, _get_cell_contents
)
import itertools

func = my_func

# 1. code 对象大小
code_args = _code_reduce(func.__code__)
code_pickled = pickle.dumps(code_args)
print(f"Code object: {len(code_pickled)} bytes")

# 2. globals 引用对象大小
f_globals_ref = _extract_code_globals(func.__code__)
f_globals = {k: func.__globals__[k] for k in f_globals_ref if k in func.__globals__}
for name, obj in f_globals.items():
    obj_pickled = pickle.dumps(obj)
    print(f"  Global '{name}' ({type(obj).__name__}): {len(obj_pickled)} bytes")

# 3. 闭包值大小
if func.__closure__ is not None:
    for i, cell in enumerate(func.__closure__):
        val = _get_cell_contents(cell)
        val_pickled = pickle.dumps(val)
        print(f"  Closure[{i}] ({type(val).__name__}): {len(val_pickled)} bytes")

# 4. 默认参数大小
if func.__defaults__:
    for i, val in enumerate(func.__defaults__):
        val_pickled = pickle.dumps(val)
        print(f"  Default arg[{i}] ({type(val).__name__}): {len(val_pickled)} bytes")

# 5. annotations 大小
if func.__annotations__:
    ann_pickled = pickle.dumps(func.__annotations__)
    print(f"Annotations: {len(ann_pickled)} bytes")
```

> 注意：方法二中各组成部分的 pickle 大小之和**不等于** total size。因为 cloudpickle 使用 pickle 协议的 memo 机制，同一对象在不同位置出现时只序列化一次（引用共享）。total size 通常小于各部分独立序列化之和。

**方法三：利用 pickle 协议的 opcodes 分析字节流**

```python
import pickletools

# 输出所有 pickle opcodes，逐条分析
pickletools.dis(pickled, annotate=True)

# 统计各类 opcode 的数量和占比
results = pickletools.genops(pickled)
opcode_counts = {}
for opcode, arg, pos in results:
    name = opcode.name
    opcode_counts[name] = opcode_counts.get(name, 0) + 1

# 找出最占体积的 STORE / GLOBAL 操作
for name, count in sorted(opcode_counts.items(), key=lambda x: -x[1]):
    print(f"  {name}: {count}")
```

`pickletools.dis` 是最细粒度的分析手段，可以看到每个对象在字节流中的确切位置和大小。

#### 2.4.3 Ray 的体积阈值检查

[utils.py:595-637](python/ray/_private/utils.py#L595-L637)

Ray 在导出函数前会调用 `check_oversized_function` 检查体积：

```python
# 阈值定义（ray_constants.py）
FUNCTION_SIZE_WARN_THRESHOLD  = 10**7   # 10 MiB → 打印警告
FUNCTION_SIZE_ERROR_THRESHOLD = 10**8   # 100 MiB → 抛出 ValueError
```

- `≤ 10 MiB`：静默通过
- `10 MiB ~ 100 MiB`：向 Driver 推送警告，提示检查闭包是否隐式捕获了大对象
- `> 100 MiB`：直接抛出 `ValueError`，拒绝导出

#### 2.4.4 减小体积的实践建议

| 问题 | 原因 | 解决方案 |
|------|------|----------|
| 函数隐式捕获大对象 | 闭包或 globals 引用了大 numpy 数组 / dict | 使用 `ray.put()` 将大对象放入 Object Store，函数中通过 ObjectRef 引用 |
| 默认参数是大对象 | `def f(data=big_list): ...` | 将默认参数改为 `None`，运行时从 Object Store 获取 |
| 模块级全局变量过大 | `MODEL = load_model()` 被函数引用 | 使用 `ray.put(MODEL)` 传参而非全局引用 |
| 类型注解引用复杂类型 | `def f(x: LargeModel): ...` | 简化注解或使用字符串注解 `"LargeModel"` |

## 3. Function Descriptor — 函数的唯一标识

### 3.1 PythonFunctionDescriptor 结构

[function_descriptor.pxi:152-336](python/ray/includes/function_descriptor.pxi#L152-L336)

`PythonFunctionDescriptor` 是一个 Cython 类，包含四个字段：

| 字段 | 说明 | 示例 |
|------|------|------|
| `module_name` | 函数所属模块 | `my_module` |
| `function_name` | 函数的 `__qualname__` | `my_func` |
| `class_name` | 类名（空字符串表示非方法） | `MyClass` |
| `function_hash` | UUID hex，保证唯一性 | `a3f2...` |

### 3.2 from_function — 远程函数

```python
@classmethod
def from_function(cls, function, function_uuid):
    module_name = cls._get_module_name(function)
    function_name = function.__qualname__
    class_name = ""
    return cls(module_name, function_name, class_name, function_uuid.hex)
```

- `function_name` 使用 `__qualname__` 而非 `__name__`，支持嵌套函数的完整路径
- `function_hash` 使用 `function_uuid.hex`，而非函数源码哈希。注释说明原因：**cloudpickle 对同一函数的序列化结果不稳定**（不同 pickle 调用可能产生不同字节），所以不能用 pickle bytes 作为 ID
- `_get_module_name`：如果模块是 `__main__`，尝试通过 `inspect.getfile` 获取真实文件对应的模块名

### 3.3 from_class — Actor 类

```python
@classmethod
def from_class(cls, target_class):
    module_name = cls._get_module_name(target_class)
    class_name = target_class.__qualname__
    return cls(module_name, "__init__", class_name, uuid.uuid4().hex)
```

Actor descriptor 的 `function_name` 固定为 `"__init__"`，`class_name` 为类名，`function_hash` 用新的随机 UUID 解决同名 Actor 冲突。

### 3.4 function_id 的计算

[function_descriptor.pxi:290-307](python/ray/includes/function_descriptor.pxi#L290-L307)

```python
def _get_function_id(self):
    function_id_hash = hashlib.shake_128()
    function_id_hash.update(self.typed_descriptor.ModuleName())
    function_id_hash.update(self.typed_descriptor.FunctionName())
    function_id_hash.update(self.typed_descriptor.ClassName())
    function_id_hash.update(self.typed_descriptor.FunctionHash())
    function_id = function_id_hash.digest(ray_constants.ID_SIZE)
    return ray.FunctionID(function_id)
```

`function_id` 由四个字段的 `shake_128` 哈希生成，是函数在 Ray 系统中的全局唯一标识。

## 4. 导出至 GCS — 序列化数据的存储

### 4.1 export 流程

[function_manager.py:196-243](python/ray/_private/function_manager.py#L196-L243)

`FunctionActorManager.export()` 将序列化后的函数存入 GCS KV 存储：

```python
def export(self, remote_function):
    function = remote_function._function
    pickled_function = remote_function._pickled_function

    # 检查函数大小是否超限
    check_oversized_function(pickled_function, ...)

    # 构建 GCS key: "RemoteFunction:<job_id_hex>:<function_id_hex>"
    key = make_function_table_key(
        b"RemoteFunction",
        self._worker.current_job_id,
        remote_function._function_descriptor.function_id.binary(),
    )

    # 如果 key 已存在，跳过（避免重复写入）
    if self._worker.gcs_client.internal_kv_exists(key, KV_NAMESPACE_FUNCTION_TABLE):
        return

    # 构建值：再次 pickle 一个字典包裹元数据和序列化函数
    val = pickle.dumps({
        "job_id": ...,
        "function_id": ...,
        "function_name": ...,
        "module": function.__module__,
        "function": pickled_function,     # ← 已经是 cloudpickle 序列化的 bytes
        "collision_identifier": ...,      # 用于检测重复导出
        "max_calls": ...,
    })

    # 写入 GCS
    self._worker.gcs_client.internal_kv_put(key, val, True, KV_NAMESPACE_FUNCTION_TABLE)
```

注意**两层 pickle**：
1. 内层：`pickled_function` = `cloudpickle.dumps(原始函数)` → 序列化函数本身
2. 外层：`pickle.dumps(字典)` → 序列化包含 `pickled_function` 的元信息字典

## 5. 反序列化 — Worker 端

### 5.1 函数注册：fetch_and_register_remote_function

[function_manager.py:265-331](python/ray/_private/function_manager.py#L265-L331)

Worker 的 Import Thread 监听 GCS 中的新函数 key，调用 `fetch_and_register_remote_function`：

```python
def fetch_and_register_remote_function(self, key):
    remote_function_info = self.fetch_registered_method(key)
    # remote_function_info 包含: job_id, function_id, function_name,
    #                              serialized_function, module, max_calls

    with self.lock:
        self._num_task_executions[function_id] = 0

        try:
            # ← 关键：反序列化函数
            function = pickle.loads(serialized_function)
        except Exception:
            # 反序列化失败：创建占位函数，执行时抛出 RuntimeError
            traceback_str = format_error_message(traceback.format_exc())

            def f(*args, **kwargs):
                raise RuntimeError(
                    "The remote function failed to import on the worker. ..."
                )

            self._function_execution_info[function_id] = FunctionExecutionInfo(
                function=f, function_name=function_name, max_calls=max_calls
            )
        else:
            # 修正 module：Driver 端 __main__ → Worker 端不同模块
            function.__module__ = module
            self._function_execution_info[function_id] = FunctionExecutionInfo(
                function=function, function_name=function_name, max_calls=max_calls
            )
    return True
```

关键细节：
- `pickle.loads(serialized_function)` 使用 **标准 pickle**（而非 cloudpickle）反序列化。因为 cloudpickle 序列化出的格式兼容标准 pickle 的 `loads`
- 反序列化失败时**不崩溃**，而是注册一个"占位函数"，在调用时抛出详细错误。这保证 Worker 进程存活，错误信息可传递回 Driver
- **module 修正**：Driver 中 `__main__` 模块定义的函数在 Worker 中 `__main__` 是 `default_worker.py`，所以必须将 `function.__module__` 设为 Driver 端的真实模块名

## 8. 关键设计决策与注意事项

### 8.1 为什么用 cloudpickle 而不是标准 pickle

标准 pickle 序列化函数时只记录 `(module_name, function_name)`，反序列化时通过 `import` 从模块中查找。这在分布式系统中不可行：
- Worker 进程没有 Driver 的源文件（尤其是 REPL 中定义的函数）
- 函数可能有闭包变量，标准 pickle 不序列化闭包内容
- `__main__` 模块在 Driver 和 Worker 中完全不同

cloudpickle 序列化**函数字节码 + 闭包变量**，让函数可被完全还原。

### 8.2 两层 pickle 设计

- **内层** `cloudpickle.dumps(function)`：序列化函数本身，使用 cloudpickle 的特殊格式
- **外层** `pickle.dumps(metadata_dict)`：序列化元信息字典，使用标准 pickle

反序列化时：
- **外层** `pickle.loads(val)`：标准 pickle 反序列化元信息字典，取出 `pickled_function` bytes
- **内层** `pickle.loads(serialized_function)`：反序列化还原函数对象（兼容标准 `loads`）

外层用标准 pickle 因为字典是简单结构，无需 cloudpickle 的特殊处理。

### 8.3 function_uuid 而非 pickle bytes 作为 hash

[function_descriptor.pxi:197-199](python/ray/includes/function_descriptor.pxi#L197-L199)

注释明确说明：

> Used to uniquely identify a function. Ideally we can use the pickled function bytes but cloudpickle isn't stable in some cases for the same function.

cloudpickle 对同一函数两次 `dumps` 可能产生不同字节（因为内存地址等不稳定因素），因此用 UUID 而非 pickle bytes 计算 function_id。

### 8.4 module 修正

[function_manager.py:326-327](python/ray/_private/function_manager.py#L326-L327)

```python
function.__module__ = module  # Driver端真实module名，而非Worker端的 __main__
```

Driver 中 `__main__` 定义的函数，在 Worker 反序列化后 `__module__` 仍是 `__main__`，但 Worker 的 `__main__` 是 `default_worker.py`。修正为 Driver 的真实模块名确保模块引用正确。

### 8.5 反序列化失败容错

Worker 反序列化失败时**不退出进程**，而是注册占位函数。调用时才抛出 RuntimeError，错误信息通过 Ray 的错误推送机制传递回 Driver。这对集群稳定性至关重要——一个函数的反序列化失败不应导致整个 Worker 进程死亡。

### 8.6 重新序列化机制

[remote_function.py:357-365](python/ray/remote_function.py#L357-L365)

同一 Driver 的第二次调用**不重新序列化**（`_last_export_cluster_and_job` 匹配）。但新的 Driver（新的 cluster/job）会重新 pickle，确保闭包变量的最新值被捕获。

### 8.7 序列化大小检查

`check_oversized_function` 在导出前检查序列化后的 bytes 是否过大。超过阈值的函数会打印警告，避免占用过多 GCS 存储或网络带宽。

## 9. Actor 方法的序列化差异

Actor 的序列化与远程函数有本质区别：

| 方面 | 远程函数 | Actor 类 |
|------|---------|---------|
| 序列化对象 | 单个函数 | 整个类（包含所有方法） |
| Descriptor function_name | 函数 `__qualname__` | `"__init__"` |
| Descriptor class_name | `""` | 类的 `__qualname__` |
| 方法注册 | 单个 `_function_execution_info` | 遍历所有方法，每个方法一个 executor |
| 方法执行 | 直接调用 | `_make_actor_method_executor` 包装，传入 actor 实例 |

Actor 类序列化时，cloudpickle 序列化**整个类定义**，Worker 反序列化后得到完整的类对象，然后通过 `inspect.getmembers` 提取所有方法并为每个方法创建 `FunctionExecutionInfo`。


# GCS 清理 Pickled Function/Actor 时机
