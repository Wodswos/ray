# Ray Core: Autoscaler v2 架构详解

> 版本: Ray 2.53.0
> 核心目录: `python/ray/autoscaler/v2/`

## 1. 全局架构概览

Ray Autoscaler v2 是一个**基于声明式状态 reconciliation** 的控制器系统，运行在 head node 上作为独立 monitor 进程，每隔 `AUTOSCALER_UPDATE_INTERVAL_S`（默认 5 秒）执行一次完整的 reconcile 循环。

## 2. 组件详解

### 2.1 AutoscalerMonitor — 主循环守护进程

**文件**: `python/ray/autoscaler/v2/monitor.py`
**类**: `AutoscalerMonitor`

这是 autoscaler 的入口进程，作为独立守护进程运行在 head node 上。

```python
class AutoscalerMonitor:
    def __init__(self, address, config_reader, log_dir, monitor_ip):
        self.gcs_client = GcsClient(address)     # 连接 GCS
        self.autoscaler = Autoscaler(...)         # 初始化 autoscaler

    def _run(self):
        """主循环: 每轮执行 autoscaler 更新并报告状态"""
        while True:
            autoscaling_state = self.autoscaler.update_autoscaling_state()
            if autoscaling_state:
                self._report_autoscaling_state(self.gcs_client, autoscaling_state)
            time.sleep(AUTOSCALER_UPDATE_INTERVAL_S)  # 默认 5s
```

**关键职责**:
1. 启动 Prometheus metrics server（可选）
2. 每轮调用 `Autoscaler.update_autoscaling_state()`
3. 将 `AutoscalingState` 通过 `GcsClient.report_autoscaling_state()` 报告给 GCS
4. 支持两种配置模式:
   - `FileConfigReader`: 从 YAML 文件读取（传统云部署）
   - `ReadOnlyProviderConfigReader`: 从 GCS 动态推断（本地模式/laptop mode）

**启动参数**:
- `--gcs-address`: GCS 服务地址
- `--autoscaling-config`: 配置文件路径（可选）
- `--monitor-ip`: monitor 进程 IP（用于 metrics server）

### 2.2 Autoscaler — 控制器核心

**文件**: `python/ray/autoscaler/v2/autoscaler.py`
**类**: `Autoscaler`

Autoscaler 是整个系统的编排器，负责初始化所有子组件并协调单轮 reconcile。

```python
class Autoscaler:
    def __init__(self, session_name, config_reader, gcs_client, ...):
        # 1. 初始化云实例 provider
        self._init_cloud_instance_provider(config, config_reader)
        # 2. 初始化 InstanceManager + subscribers
        self._init_instance_manager(session_name, config, cloud_provider, gcs_client)
        # 3. 初始化 Scheduler
        self._scheduler = ResourceDemandScheduler(self._event_logger)

    def update_autoscaling_state(self) -> Optional[AutoscalingState]:
        # 1. 获取集群资源状态
        ray_cluster_resource_state = get_cluster_resource_state(self._gcs_client)
        # 2. 刷新配置
        self._config_reader.refresh_cached_autoscaling_config()
        # 3. 调用 Reconciler
        return Reconciler.reconcile(
            instance_manager=self._instance_manager,
            scheduler=self._scheduler,
            cloud_provider=self._cloud_instance_provider,
            ray_cluster_resource_state=ray_cluster_resource_state,
            non_terminated_cloud_instances=self._cloud_instance_provider.get_non_terminated(),
            cloud_provider_errors=self._cloud_instance_provider.poll_errors(),
            ...
        )
```

**云实例 Provider 初始化策略**（`_init_cloud_instance_provider`）:

| Provider 类型 | 初始化方式 | 适用场景 |
|---|---|---|
| `kuberay` | `KubeRayProvider` | Kubernetes 部署 |
| `readonly` | `ReadOnlyProvider` | 本地模式/laptop mode |
| 其他 (aws/gcp/azure...) | `NodeProviderAdapter` 包裹 v1 `NodeProvider` | 传统云部署 |

**InstanceManager subscribers 初始化**（`_init_instance_manager`）:

| Subscriber | 触发条件 | 动作 |
|---|---|---|
| `CloudInstanceUpdater` | `REQUESTED` / `TERMINATING` 状态变更 | 调用云 API launch/terminate |
| `RayStopper` | `RAY_STOP_REQUESTED` 状态变更 | 通过 GCS drain Ray node |
| `ThreadedRayInstaller` | `RAY_INSTALLING` 状态变更 | SSH 到节点安装 Ray（仅 NodeProviderAdapter） |
| `CloudResourceMonitor` | 所有状态变更 | 跟踪云资源可用性评分 |

### 2.3 Reconciler — 状态协调器

**文件**: `python/ray/autoscaler/v2/instance_manager/reconciler.py`
**类**: `Reconciler`

Reconciler 是 autoscaler 的核心逻辑引擎，实现了**声明式 reconciliation 模式**：每轮先被动同步外部状态，再主动推进目标状态。

#### 2.3.1 reconcile() 主流程

```python
@staticmethod
def reconcile(...) -> AutoscalingState:
    autoscaling_state = AutoscalingState()

    # Phase 1: 被动状态同步 — 只反映外部真实状态，不触发任何副作用
    Reconciler._sync_from(
        instance_manager, ray_nodes, non_terminated_cloud_instances,
        cloud_provider_errors, ray_install_errors, ray_stop_errors,
        autoscaling_config,
    )

    # Phase 2: 主动状态推进 — 计算并触发决策性的状态变更
    Reconciler._step_next(
        autoscaling_state, instance_manager, scheduler,
        cloud_provider, ray_cluster_resource_state,
        non_terminated_cloud_instances, autoscaling_config,
    )

    # Phase 3: 报告 metrics
    Reconciler._report_metrics(instance_manager, autoscaling_config, metrics_reporter)

    return autoscaling_state
```

#### 2.3.2 _sync_from() — 被动状态同步

处理 9 种状态转换，全部是**被动**的（只反映外部事实，不主动改变）：

| # | 转换 | 触发条件 | 意义 |
|---|---|---|---|
| 1 | `QUEUED/REQUESTED → ALLOCATED` | 云实例分配成功 | IM 请求的云实例已创建 |
| 2 | `REQUESTED → ALLOCATION_FAILED` | 云 API 报错 launch 失败 | 云端创建失败 |
| 3 | `ALLOCATED → ALLOCATION_TIMEOUT` | ALLOCATED 超时 stuck | 云实例已创建但 Ray 启动卡住 |
| 4 | `* → RAY_RUNNING` | Ray node 加入集群 | 节点上的 Ray 正常运行 |
| 5 | `* → TERMINATED` | 云实例已终止 | 云端实例消失 |
| 6 | `TERMINATING → TERMINATION_FAILED` | 云 API 报错 terminate 失败 | 云端终止失败 |
| 7 | `* → RAY_STOPPED` | Ray node 已停止 | Ray 进程已退出 |
| 8 | `* → RAY_INSTALL_FAILED` | RayInstaller 报错 | Ray 安装失败 |
| 9 | `RAY_STOP_REQUESTED → RAY_RUNNING` | RayStopper 报错 (e.g. drain rejected) | drain 被拒绝，回退到 running |

额外处理：`_handle_extra_cloud_instances` — 对于不在 IM 中但存在于云/Ray 中的实例，创建新的 ALLOCATED IM instance。

#### 2.3.3 _step_next() — 主动状态推进

7 个步骤按顺序执行：

| 步骤 | 方法 | 意义 |
|---|---|---|
| 1 | `_handle_stuck_instances` | 超时处理 stuck 实例 |
| 2 | `_scale_cluster` | Scheduler 决策 → 创建 QUEUED/TERMINATING |
| 3 | `_handle_instances_launch` | QUEUED → REQUESTED (触发云 API launch) |
| 4 | `_terminate_instances` | RAY_STOPPED/ALLOCATION_TIMEOUT/... → TERMINATING |
| 5 | `_install_ray` | ALLOCATED → RAY_INSTALLING |
| 6 | `_fill_autoscaling_state` | 汇总 IM 状态填充 AutoscalingState protobuf |

**_scale_cluster() 核心逻辑**:

```python
# 构建调度请求
sched_request = SchedulingRequest(
    node_type_configs=autoscaling_config.get_node_type_configs(),
    max_num_nodes=autoscaling_config.get_max_num_nodes(),
    resource_requests=ray_state.pending_resource_requests,
    gang_resource_requests=ray_state.pending_gang_resource_requests,
    cluster_resource_constraints=ray_state.cluster_resource_constraints,
    current_instances=autoscaler_instances,    # IM + Ray 融合视图
    idle_timeout_s=autoscaling_config.get_idle_timeout_s(),
    cloud_resource_availabilities=cloud_resource_monitor.get_resource_availabilities(),
)

# 调用 scheduler
reply = scheduler.schedule(sched_request)

# 应用决策:
for terminate_request in reply.to_terminate:
    # → RAY_STOP_REQUESTED 或 TERMINATING
for launch_request in reply.to_launch:
    # 创建新 IM instance → QUEUED
```

**_handle_instances_launch() — launch 限速逻辑**:

```python
# 限速参数
upscaling_speed = autoscaling_config.get_upscaling_speed()  # 默认 1.0
max_concurrent_launches = AUTOSCALER_MAX_CONCURRENT_LAUNCHES  # 默认 5

# 每种 node type 的最大 pending 数 = upscaling_speed * max(running_count, 1)
# 全局并发限制 = max_concurrent_launches - total_num_requested_to_launch
```

**状态转换校验** — `InstanceUtil.set_status(instance, new_status)` 确保只有合法的状态转换：

```
QUEUED ─→ REQUESTED ─→ ALLOCATED ─→ RAY_INSTALLING ─→ RAY_RUNNING
  │          │             │               │                │
  │          │             │               │                ├→ RAY_STOP_REQUESTED
  │          │             │               │                │       ├→ RAY_STOPPING ─→ RAY_STOPPED ─→ TERMINATING ─→ TERMINATED
  │          │             │               ├→ RAY_INSTALL_FAILED ─→ TERMINATING ─→ TERMINATED
  │          ├→ ALLOCATION_FAILED (终态)
  │          │
  └─→ ALLOCATION_TIMEOUT ─→ TERMINATING ─→ TERMINATED
                                    │
                                    ├→ TERMINATION_FAILED ─→ TERMINATING (retry)
```

**允许创建新 instance 的初始状态**: `ALLOCATED`（head node），`QUEUED`（新 worker），`TERMINATING`（leaked instance）

### 2.5 ResourceDemandScheduler — 资源调度决策器

**文件**: `python/ray/autoscaler/v2/scheduler.py`
**类**: `ResourceDemandScheduler`

Scheduler 是 autoscaler 的**决策大脑**，决定集群应该扩展到什么形状。

#### 2.5.1 schedule() 8 步算法

```python
def schedule(self, request: SchedulingRequest) -> SchedulingReply:
    ctx = ScheduleContext.from_schedule_request(request)

    # Step 1: 终止 outdated nodes (launch_config_hash 变更)
    _terminate_outdated_nodes(ctx)

    # Step 2: 保证每种 node type 的 min_workers
    _enforce_min_workers_per_type(ctx)

    # Step 3: 限制每种 node type 的 max_workers
    _enforce_max_workers_per_type(ctx)

    # Step 4: 限制全局 max workers
    _enforce_max_workers_global(ctx)

    # Step 5: 保证 cluster resource constraints (SDK request_resources)
    infeasible_constraints = _enforce_resource_constraints(ctx, constraints)

    # Step 6: 调度 gang resource requests (placement groups)
    infeasible_gang_requests = _sched_gang_resource_requests(ctx, gang_requests)

    # Step 7: 调度 tasks/actors resource requests
    infeasible_requests = _sched_resource_requests(ctx, requests)

    # Step 8: 终止 idle nodes
    _enforce_idle_termination(ctx)

    return SchedulingReply(
        to_launch=ctx.get_launch_requests(),
        to_terminate=ctx.get_terminate_requests(),
        infeasible_resource_requests=infeasible_requests,
        ...
    )
```

#### 2.5.2 SchedulingNode — 调度抽象

每个 `SchedulingNode` 代表一个可调度的节点（已存在或待创建），包含：

| 属性 | 说明 |
|---|---|
| `node_type` | 节点类型名称 (e.g. "cpu_4_ondemand") |
| `status` | `TO_LAUNCH` / `SCHEDULABLE` / `TO_TERMINATE` |
| `total_resources` | 节点总资源 |
| `available_resources_for_sched` | 按来源分 (PENDING_DEMAND / CLUSTER_RESOURCE_CONSTRAINT) |
| `labels` | 节点标签（用于 anti-affinity / spread PG） |
| `idle_duration_ms` | 空闲时间 |
| `launch_config_hash` | 用于检测配置变更 |
| `termination_request` | 终止请求（包含原因） |

#### 2.5.3 Scoring 函数 — 节点选择策略

`_compute_score()` 返回一个 5 元组 `(matches_labels, gpu_ok, num_matching_resource_types, min_util, avg_util)`:

| 优先级 | 因素 | 说明 |
|---|---|---|
| 1 | `matches_labels` | 标签约束匹配度 |
| 2 | `gpu_ok` | 避免将非 GPU 任务放到 GPU 节点 |
| 3 | `num_matching_resource_types` | 匹配的资源种类数 |
| 4 | `min_util` | 最小利用率（用 v × util³ 加权） |
| 5 | `avg_util` | 平均利用率 |

**排序时还叠加 `cloud_resource_availabilities`** — 近期云 API 失败率高的 node type 会被降权。

#### 2.5.4 _try_schedule() — Bin-Packing 算法

```python
# 先在已有节点上调度
while requests and existing_nodes:
    best_node, requests, existing_nodes = _sched_best_node(requests, existing_nodes, ...)
    target_nodes.append(best_node)

# 再在新节点上调度（按 node_type_configs 创建虚拟节点）
while requests and node_pools:
    best_node, requests, node_pools = _sched_best_node(requests, node_pools, ...)
    target_nodes.append(best_node)
    # 如果该 node type 还有余量，添加新的虚拟节点到 pool
```

**_sched_best_node()**: 贪心策略 — 对每个候选节点尝试调度所有请求，计算 score，选 score 最高的。

#### 2.5.5 Gang Resource Requests — Placement Group 处理

| PG 策略 | 调度方式 |
|---|---|
| `STRICT_PACK` | 合并所有 bundle 为一个请求，尝试放在单节点 |
| `PACK/SPREAD` | 转为普通 resource demand vector |
| `STRICT_SPREAD` | 使用 anti-affinity label constraint，每个 bundle 必须在不同节点 |

**原子性**: gang request 要么全部调度成功，要么全部不调度。

#### 2.5.6 Idle Termination

节点满足以下所有条件时被终止：
1. idle 时间 > `idle_timeout_s`
2. 没有 PENDING_DEMAND 调度请求
3. 没有 CLUSTER_RESOURCE_CONSTRAINT 调度请求
4. 不受 `min_worker_nodes` 保护

## 4. 关键算法详解

### 4.1 Upscaling Speed — 扩展限速

```python
# _compute_to_launch() 中的限速逻辑
for instance_type, queued_instances_for_type in queued_instances_by_type.items():
    running_instances_for_type = running_instances_by_type.get(instance_type, [])

    # 每种 type 的最大 pending = upscaling_speed * max(running, 1)
    num_desired_to_upscale = max(1, math.ceil(upscaling_speed * max(len(running), 1)))

    # 全局限制: 已有 requested + 本次 to_launch ≤ max_concurrent_launches
    num_to_launch = min(
        max_concurrent_launches - total_num_requested_to_launch,
        num_desired_to_upscale,
    )
```

**示例**: `upscaling_speed=0.5`, 3 个 running worker → 最多 launch `ceil(0.5 * 3) = 2` 个新 worker。

### 4.2 Node 选择排序 — 终止优先级

```python
# _sort_nodes_for_termination() 排序 (升序, 先终止排前面的):
return (
    running_ray,       # 1. Ray 还没启动的先终止
    -idle_duration_ms, # 2. 空闲最久的先终止
    avg_util,          # 3. 利用率最低的先终止
)
```

### 4.3 Outdated Node 检测

```python
# 当 node_type_config 的 launch_config_hash 与 instance 的不匹配时
# → 节点标记为 TO_TERMINATE
# 配置变更场景: 用户修改了 YAML 中的 node_config
# 注意: Head node 永远不会被终止 (只会 warn)
```

### 4.4 Extra Cloud Instance 处理

Reconciler 处理不在 IM 中但存在于云/Ray 中的实例：

1. **从云 provider 发现的** → 创建 ALLOCATED IM instance（可能是 leaked 或 out-of-band）
2. **从 Ray node 发现的** → 创建 ALLOCATED IM instance（Ray node 的 instance_id 不在 IM 中）

这些 extra instance 会：
- 如果 Ray 正常运行 → 纳入调度（可作为 SCHEDULABLE node）
- 如果 Ray 不运行 → ALLOCATION_TIMEOUT 超时后终止

      └──────────────────────────────────────────────────────────────────┘

t9    sleep(AUTOSCALER_UPDATE_INTERVAL_S)  → 下一轮
```

## 9. 常见场景分析

### 9.1 新 Task 提交 → 集群扩展

```
用户: ray.remote(num_cpus=4)(my_task)

1. Raylet 提交 task → GCS 调度队列
2. GCS 收集 resource load → pending_resource_requests += {CPU: 4}

   a. get_cluster_resource_state() → 拿到 demands

      - Reply.to_launch += LaunchRequest(instance_type="cpu_4_ondemand", count=1)
      - 创建 IM instance → QUEUED
   c. _handle_instances_launch(): QUEUED → REQUESTED
   d. CloudInstanceUpdater: REQUESTED → cloud_provider.launch(shape={"cpu_4_ondemand": 1})
4. 云 API 创建实例 → 下一轮 _sync_from():
   - REQUESTED → ALLOCATED (匹配到云实例)
   - _install_ray(): ALLOCATED → RAY_INSTALLING
   - ThreadedRayInstaller: SSH 安装 Ray
   - Ray node 加入集群 → _sync_from(): RAY_INSTALLING → RAY_RUNNING
5. GCS 调度 task 到新节点
```

### 9.2 Placement Group 创建 → GANG 调度

```
用户: ray.util.placement_group([{"CPU": 2}, {"CPU": 2}, {"GPU": 1}], strategy="STRICT_SPREAD")

1. GCS PlacementGroupManager → pending_gang_resource_requests += GangResourceRequest
   - 3 个 bundle，带 anti-affinity constraints
2. Scheduler._sched_gang_resource_requests():
   - 原子性调度: 3 个 bundle 必须全部成功
   - STRICT_SPREAD: 每个 bundle 使用 anti-affinity label → 必须在不同节点
   - 可能需要 3 个新节点
3. 同 9.1 的节点创建流程
```

### 9.3 Idle Node 缩减

```
1. Raylet 报告 node idle → GCS node_state.idle_duration_ms 增加
2. Scheduler._enforce_idle_termination():
   - idle_duration_ms > idle_timeout_s
   - 无 PENDING_DEMAND 需求
   - 无 CLUSTER_RESOURCE_CONSTRAINT 需求

## 9.5 ALLOCATION_TIMEOUT 与 Pod 误删分析（KubeRay 场景）

> 场景来源: KubeRay 集群中 pod 上 Ray 启动耗时超过 `allocate_status_timeout_s` (默认 300s)

### 9.5.1 ALLOCATED 状态详解

**ALLOCATED = "云实例已存在，但 Ray 还没注册到 GCS"**

这是一个中间过渡状态，覆盖从云实例被发现到 Ray 成功注册之间的所有时间。

#### 对应的 Kubernetes Pod 状态

`ALLOCATED` 不是对应某个特定的 pod phase。KubeRay provider 的 `_fetch_instances()` 会返回**所有 pod**（不管 Pending 还是 Running），只要没有 `deletionTimestamp`：

| Pod 实际状态 | `_is_running()` | IM 行为 |
|-------------|-----------------|---------|
| Pending（等待调度） | `False` | ALLOCATED（卡住等 pod Running） |
| ContainerCreating（拉镜像） | `False` | ALLOCATED（同上） |
| Running（容器运行中，Ray 启动中） | `True` | ALLOCATED → 等待 Ray 注册 |
| Running + Ray 注册成功 | `True` | ALLOCATED → **RAY_RUNNING** ✅ |

关键代码 ([cloud_provider.py:558-577](python/ray/autoscaler/v2/instance_manager/cloud_providers/kuberay/cloud_provider.py#L558-L577))：

```python
@staticmethod
def _is_running(pod) -> bool:
    # pod 还没 containerStatus → False (Pending/ContainerCreating)
    if "containerStatuses" not in pod["status"]
       or not pod["status"]["containerStatuses"]:
        return False
    # container 状态不是 running → False
    state = pod["status"]["containerStatuses"][0]["state"]
    if "running" in state:
        return True  # ← 只有容器真正在运行才算 True
    return False
```

#### REQUESTED → ALLOCATED 的两条路径

**路径 A: 主动分配** ([reconciler.py:317-379](python/ray/autoscaler/v2/instance_manager/reconciler.py#L317-L379))

```
QUEUED → REQUESTED → ALLOCATED
```

1. `_scale_cluster` 决定需要新实例 → 创建 IMInstance (QUEUED)
2. `_handle_instances_launch` 把 QUEUED → REQUESTED（向云提供商发出创建 pod 请求）
3. `_handle_cloud_instance_allocation` 发现云提供商返回了未分配的同类型 pod → REQUESTED → ALLOCATED

匹配逻辑只看 `instance_type`（[reconciler.py:409-412](python/ray/autoscaler/v2/instance_manager/reconciler.py#L409-L412)），**不检查 pod 是否 Running**：

```python
if len(unassigned_cloud_instances_by_type.get(im_instance.instance_type, [])):
    unassigned_cloud_instance = unassigned_cloud_instances_by_type[
        im_instance.instance_type
    ].pop()
```

**路径 B: 被动发现** ([reconciler.py:1512-1554](python/ray/autoscaler/v2/instance_manager/reconciler.py#L1512-L1554))

当 reconciler 发现一个 pod 不被任何活跃 IMInstance 管理时，直接创建新 IMInstance 为 ALLOCATED：

```python
updates[cloud_instance_id] = IMInstanceUpdateEvent(
    instance_id=InstanceUtil.random_instance_id(),
    new_instance_status=IMInstance.ALLOCATED,
    details="allocated unmanaged cloud instance :...",
    upsert=True,
)
```

#### ALLOCATED → 下一状态

| 转换 | 条件 | 代码位置 |
|------|------|---------|
| ALLOCATED → RAY_RUNNING | Ray node 注册到 GCS，状态 RUNNING/IDLE | `_handle_ray_status_transition` |
| ALLOCATED → RAY_INSTALLING | Pod Running (`is_running=True`) 且需要 SSH 安装 Ray | `_install_ray`（KubeRay 场景跳过） |
| ALLOCATED → ALLOCATION_TIMEOUT | 超过 `allocate_status_timeout_s` (默认 300s) | `_handle_stuck_instances` |
| ALLOCATED → TERMINATED | Pod 从云提供商消失 | `_handle_cloud_instance_terminated` |

---

### 9.5.2 删除请求完整链路

从 ALLOCATION_TIMEOUT 到 pod 实际被删除，经过 5 步：

```
Step 1: 超时判定
  reconciler.py:948  _handle_stuck_instances()
  ALLOCATED → ALLOCATION_TIMEOUT (instance 被标记超时)

Step 2: 决定终止
  reconciler.py:1234-1249  _terminate_instances()
  扫描所有 ALLOCATION_TIMEOUT 的实例
  ALLOCATION_TIMEOUT → TERMINATING
  创建 IMInstanceUpdateEvent(new_status=TERMINATING)

Step 3: Subscriber 触发删除
  cloud_instance_updater.py:34-63  notify()
  InstanceManager 在状态变更后通知所有 subscriber
  CloudInstanceUpdater 篮选出 TERMINATING 事件
  → 调用 _terminate_instances()
  → 调用 cloud_provider.terminate(ids=[pod_names])

Step 4: KubeRay Provider 构造 ScaleRequest
  kuberay/cloud_provider.py:116-143  terminate()
  创建 ScaleRequest(to_launch={}, to_delete=[pod_names])
  调用 _submit_scale_request()
  日志: "Terminating worker pods: [...]"

Step 5: Patch K8s API 删除 Pod
  kuberay/cloud_provider.py:329-370  _submit_scale_request()
  构造 JSON Patch:
    path: /spec/workerGroupSpecs/{group_index}/scaleStrategy
    value: {"workersToDelete": ["pod-name-1", "pod-name-2", ...]}
  调用 K8s API: PATCH rayclusters/{cluster_name}
  → KubeRay Operator 看到 workersToDelete 更新
  → 删除对应 Pod
```

删除是不可逆的——一旦 PATCH 发出，KubeRay Operator 就会执行 pod 删除，没有取消机制。

### 9.5.3 实际案例：Pod 误删时序分析

**日志来源**: KubeRay 集群, pod `boltzgen-v2-model-group-cpu-worker-cnxwt`

#### 时间线

| 时间 | Instance ID | 状态转换 | cloud_instance_id | ray_id |
|------|------------|---------|-------------------|--------|
| 10:08:40 | **9c8efbae** | REQUESTED→ALLOCATED | boltzgen-...-cnxwt | 空 |
| 10:13:46 | **9c8efbae** | ALLOCATED→ALLOCATION_TIMEOUT | boltzgen-...-cnxwt | 空 |
| 10:14:02 | **9c8efbae** | ALLOCATION_TIMEOUT→TERMINATING | boltzgen-...-cnxwt | 空 |
| 10:14:02 | — | 开始终止 pod boltzgen-...-cnxwt | | |
| 10:14:19 | **9c8efbae** | TERMINATING→TERMINATED | boltzgen-...-cnxwt | 空 |
| 10:14:19 | **b95a2a7d** | ALLOCATED→RAY_RUNNING | **同一个 pod** boltzgen-...-cnxwt | e9809fa4... |
| 10:14:28 | **b95a2a7d** | RAY_RUNNING→TERMINATED | boltzgen-...-cnxwt | e9809fa4... |

#### 关键发现

**同一个 cloud pod 被** **两个不同的 IMInstance** **跟踪了！**

- `9c8efbae`: 原始实例，因超时被终止
- `b95a2a7d`: 竞态产生的第二个实例，短暂进入 RAY_RUNNING 后也被删除

#### 双实例竞态根因

在 `10:14:19` 这轮 reconcile 中，三个条件同时满足：

1. 原实例 `9c8efbae` 已 TERMINATED → 不再被视为"管理该 cloud_instance_id"
2. Pod 在云提供商侧还在 Running（K8s 删除有延迟）
3. Ray 刚注册成功（GCS 报告了 ray node `e9809fa4`）

`_handle_extra_cloud_instances_from_cloud_provider` 的过滤条件 ([reconciler.py:1529-1535](python/ray/autoscaler/v2/instance_manager/reconciler.py#L1529-L1535))：

```python
cloud_instance_ids_managed_by_im = {
    instance.cloud_instance_id
    for instance in instances
    if instance.cloud_instance_id
    and instance.status
    not in [IMInstance.TERMINATED, IMInstance.ALLOCATION_FAILED]
}
# ↑ TERMINATED 的 IMInstance 不在集合中 → pod 被视为"未管理"
# → 创建新 IMInstance b95a2a7d → ALLOCATED
```

#### 误删结论

**Ray 在 pod 上实际启动成功了**（启动耗时约 340 秒），但：
- 超时阈值是 300 秒，在 `10:13:46` 就判定超时（距 ALLOCATED 仅 306 秒）
- `10:14:02` 发出不可逆的删除请求
- Ray 注册成功比删除请求晚了仅 **17 秒**

如果 `allocate_status_timeout_s` 设为 ≥340 秒，这个 pod 就不会被误删。

### 9.5.4 Pending Pod 循环问题（设计缺陷）

#### 问题描述

当 K8s 集群资源不足时，pod 会长时间 Pending。由于 `_handle_cloud_instance_allocation` 匹配时不检查 pod phase，Pending pod 也被当作 ALLOCATED。300 秒超时后 pod 被删除，但 Scheduler 仍需该类型 → 创建新 pod → 仍然 Pending → 再次超时删除 → **无限循环**。

#### 循环流程

```
┌───────────────────────────────────────────────────────────┐
│  Scheduler 看到 pending resource requests                   │
│  (还有任务需要 model-group-cpu 资源)                           │
└───────────────────────────┬───────────────────────────────┘
                            ↓
┌───────────────────────────────────────────────────────────┐
│  QUEUED → REQUESTED                                          │
│  (autoscaler 发出 ScaleRequest 增加 replica 数量)              │
└───────────────────────────┬───────────────────────────────┘
                            ↓
┌───────────────────────────────────────────────────────────┐
│  KubeRay 创建 Pod → Pending ← K8s 资源不足，无法调度         │
│  Pod 被 _fetch_instances 发现                                │
│  REQUESTED → ALLOCATED                                       │
└───────────────────────────┬───────────────────────────────┘
                            ↓
┌───────────────────────────────────────────────────────────┐
│  等 300 秒...                                                 │
│  ← _install_ray 跳过 (is_running=False)                       │
│  ← _handle_ray_status_transition 没匹配 (Ray 没注册)            │
│  ALLOCATED → ALLOCATION_TIMEOUT                              │
└───────────────────────────┬───────────────────────────────┘
                            ↓
┌───────────────────────────────────────────────────────────┐
│  ALLOCATION_TIMEOUT → TERMINATING                            │
│  Pod 被删除 ← 删除一个 Pending pod 没有任何用处                  │
└───────────────────────────┬───────────────────────────────┘
                            ↓
┌───────────────────────────────────────────────────────────┐
│  TERMINATED → IMInstance 消亡                                │
│  Scheduler 下次 reconcile 仍看到需求                           │
│  → 回到步骤 1 🔁                                              │
└───────────────────────────────────────────────────────────┘
```

**每轮循环浪费约 300 秒**——只是创建了一个 Pending pod 等了 5 分钟然后删掉，集群资源状况没有任何改善。

#### 根因对比

超时逻辑不区分两种完全不同的场景：

| 场景 | Pod 状态 | 根因 | 正确做法 | 实际做法 |
|------|---------|------|---------|---------|
| **Ray 启动慢** | Running (`is_running=True`) | Pod 正常运行，Ray 还没注册 | 增大超时或等 Ray 注册 | 300s 超时后删除 ❌ |
| **K8s 资源不足** | Pending (`is_running=False`) | Pod 无法调度，没机会运行 | **不应删除**，等 K8s 资源释放 | 同样 300s 超时后删除 ❌ |

`_handle_stuck_instances` ([reconciler.py:941-956](python/ray/autoscaler/v2/instance_manager/reconciler.py#L941-L956)) 对两种情况一视同仁：

```python
for instance in instances_by_status[IMInstance.ALLOCATED]:
    update = Reconciler._handle_stuck_instance(
        instance,
        reconcile_config.allocate_status_timeout_s,  # 不管 pod Pending 还是 Running
        new_status=IMInstance.ALLOCATION_TIMEOUT,     # 统一超时处理
    )
```

它没有检查 `cloud_instance.is_running`——Pending pod 和 Running pod 在超时逻辑面前毫无区别。

在 RayCluster CR 的 head pod 中设置环境变量（autoscaler 运行在 head pod 中）：

```yaml
apiVersion: ray.io/v1alpha1
kind: RayCluster
spec:
  headGroupSpec:
    template:
      spec:
        containers:
        - name: ray-head
          env:
          - name: RAY_AUTOSCALER_RECONCILE_ALLOCATE_STATUS_TIMEOUT_S
            value: "600"  # 从 300s 增大到 600s
```

## 10. 设计模式总结

| 模式 | 应用 | 说明 |
|---|---|---|
| **声明式 Reconciliation** | Reconciler | 每轮计算"期望状态"，而不是记录增量操作 |
| **Observer Pattern** | InstanceManager → Subscribers | 状态变更通知，解耦存储和执行 |
| **状态机** | Instance.InstanceStatus | 严格的状态转换校验，防止非法转换 |
| **乐观并发控制** | InstanceManager (version-based) | 单写者（Reconciler）+ 版本号防冲突 |
| **插件式架构** | ICloudInstanceProvider / IResourceScheduler / IConfigReader | 可替换的云 provider、调度器、配置源 |
| **限速** | upscaling_speed + max_concurrent_launches | 防止过快扩展导致资源浪费 |
| **超时 + Retry** | InstanceReconcileConfig | stuck instance 超时处理 + 最大 retry 次数 |
| **Passive + Active Phase** | _sync_from() + _step_next() | 先同步外部事实，再推进决策状态 |
