# Ray PubSub 系统

本文基于 `src/ray/pubsub` 的实现整理，重点说明 Ray 内部 pubsub 的结构、流程、容错和消息语义。

## 1. 系统定位

Ray 的 pubsub 更接近“进程间观察者模式”，而不是带持久化和中间 broker 的消息系统。

- 无外部 broker，publisher 直接推送给 subscriber。
- 目标是降低连接数和内存占用，不是做高吞吐消息中间件。
- 通过“单连接 long polling + 命令批处理”把连接规模从 O(#objects) 降到 O(#subscribers)。

## 2. 目录与模块分层

`src/ray/pubsub/` 主要由三层组成：

- 核心实现
  - `publisher.h/cc`
  - `subscriber.h/cc`
- 接口与适配
  - `publisher_interface.h`
  - `subscriber_interface.h`
  - `gcs_publisher.h/cc`
  - `gcs_subscriber.h/cc`
  - `python_gcs_subscriber.h/cc`
- 辅助
  - `fake_publisher.h` / `fake_subscriber.h`
  - `tests/`
  - `README.md`

## 3. 核心对象与职责

### 3.1 Subscriber 侧

- `SubscriberChannel`
  - 维护单个 channel 的订阅关系（按 publisher + key 组织）。
  - 处理消息回调 `HandlePublishedMessage`。
  - 处理失败回调 `HandlePublisherFailure`。
- `Subscriber`
  - 管理多 channel 订阅生命周期。
  - 维护每个 publisher 的 in-flight long polling。
  - 维护命令队列（subscribe/unsubscribe）并批量发送。
  - 记录 `processed_sequences_`，用于断点续传与去重。

### 3.2 Publisher 侧

- `SubscriptionIndex`
  - 每个 channel 一份索引，管理“按 key 订阅”和“订阅全部”。
- `EntityState`
  - 管理某个 key（或 all-keys）的订阅者集合和消息缓冲。
- `SubscriberState`
  - 维护单个 subscriber 的 long-poll 连接和 `mailbox_`。
  - 按 `max_processed_sequence_id` 清理已确认消息。

## 4. 通信与数据流

## 4.1 两条 RPC 通道

- `PubsubCommandBatch`：subscriber -> publisher，传递订阅/退订命令。
- `PubsubLongPolling`：subscriber -> publisher，长轮询拉取发布消息。

### 4.2 订阅建立流程

1. subscriber 本地登记订阅回调（channel + key）。
2. 把 `Subscribe` 命令入队。
3. 若当前没有 in-flight 命令请求，则发送一批 `PubsubCommandBatchRequest`。
4. 同时确保有一条 in-flight `PubsubLongPollingRequest`。

### 4.3 消息发布流程

1. publisher `Publish()` 时分配全局单调递增 `sequence_id`。
2. 按 channel/key 在 `SubscriptionIndex` 找到目标 subscriber。
3. 消息进入各 subscriber 的 `mailbox_`。
4. 若该 subscriber 当前有 long-poll 连接，立即回包（按批次发送）。

### 4.4 取消订阅流程

1. subscriber 发送 `Unsubscribe` 命令。
2. publisher 从索引中移除对应关系。
3. 若某 key 或 subscriber 无剩余关联，回收对应元数据。

## 5. 顺序性与投递语义

- 命令顺序：每个 publisher 仅允许一个 in-flight `PubsubCommandBatchRequest`，确保 subscribe/unsubscribe FIFO。
- 消息顺序：按 publisher 的 `sequence_id` 顺序处理；subscriber 对已处理序号做去重保护。
- Last command wins：最终状态以最后一次命令为准。

## 6. 超时、故障检测与重连

## 6.1 超时参数

- `subscriber_timeout_ms` 默认 `300 * 1000`（5 分钟）。
- 配置位于 `ray_config_def.h`。

### 6.2 Publisher 侧失活判断

publisher 周期执行 `CheckDeadSubscribers()`：

1. 若 subscriber 仍活跃（最近有请求/回复），不处理。
2. 若超时且仍有 in-flight long-poll，先 `force_noop` 空回复，促使对方重建连接。
3. 若后续仍无新连接，则判定 subscriber dead，清理订阅与状态。

注：实际删除延迟可能约为 `1x ~ 3x subscriber_timeout_ms`。

### 6.3 重连建立路径

- 正常路径：subscriber 每收到一轮 long-poll 回复，若仍有订阅立即发起下一轮。
- 被动刷新路径：publisher 通过空回复刷新连接，活着的 subscriber 会立刻补发 long-poll。
- 网络抖动路径：`PubsubLongPolling` 和 `PubsubCommandBatch` 走可重试 gRPC 客户端，连接恢复后自动重发可重试请求。

### 6.4 不可恢复错误

若 long-poll 回调最终返回 `status !ok`，subscriber 会触发 failure callback 并清理对应订阅。  
这通常意味着上层需要显式 resubscribe，而不是框架透明恢复全部语义。

## 7. 断连期间会不会丢消息

结论：**短暂断连通常不丢；长时断连或边界场景会丢。**

### 7.1 为什么短暂断连通常不丢

- publisher 为每条消息分配 `sequence_id`。
- subscriber 在下一次 long-poll 请求里上报 `max_processed_sequence_id`。
- publisher 只删除 `sequence_id <= max_processed_sequence_id` 的消息。
- 未确认消息保留在 `mailbox_` 并可重发，因此能“断点续传”。

### 7.2 什么时候会丢

1. 订阅建立前发布：消息天然丢失（模块已声明的限制）。
2. 断连过久被判 dead：publisher 清理订阅后，后续消息不再进入该 subscriber mailbox。
3. 非关键频道触发缓冲上限：如 `RAY_ERROR_INFO_CHANNEL` / `RAY_LOG_CHANNEL` / `RAY_NODE_RESOURCE_USAGE_CHANNEL`，可能因 `publisher_entity_buffer_max_bytes` 丢弃最旧消息。

补充：对象生命周期和部分 GCS 关键频道默认 `max_buffered_bytes = -1`，不会因该上限主动丢弃，但仍受订阅状态与进程存活影响。

## 8. 典型频道与使用场景

- 对象与引用管理
  - `WORKER_OBJECT_LOCATIONS_CHANNEL`
  - `WORKER_OBJECT_EVICTION`
  - `WORKER_REF_REMOVED_CHANNEL`
- GCS 状态广播
  - `GCS_ACTOR_CHANNEL`
  - `GCS_JOB_CHANNEL`
  - `GCS_NODE_INFO_CHANNEL`
  - `GCS_WORKER_DELTA_CHANNEL`
  - `GCS_NODE_ADDRESS_AND_LIVENESS_CHANNEL`
- 日志与错误分发
  - `RAY_ERROR_INFO_CHANNEL`
  - `RAY_LOG_CHANNEL`

## 9. 关键配置速览

- `subscriber_timeout_ms`：subscriber 失活判定超时（默认 300s）。
- `max_command_batch_size`：每次命令批处理上限。
- `publish_batch_size`：单次 long-poll 回复的消息条数上限。
- `publisher_entity_buffer_max_bytes`：部分频道的实体缓冲上限。

## 10. 一句话总结

Ray pubsub 的可靠性基础不是 broker 持久化，而是 **publisher 内存 mailbox + sequence ack 的会话内重传**。  
它能较好覆盖短时网络抖动，但不保证长时离线后的历史补偿。
